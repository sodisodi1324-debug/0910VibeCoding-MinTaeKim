# Project Review

이 프로젝트의 코드와 문서를 실제로 읽고, 아래 세 가지 질문에 **순서대로** 답한다. 짐작하지 말고 반드시 프로젝트 안의 파일을 열어서 확인한 다음 답할 것.

## 진행 방법

1. 먼저 프로젝트를 파악한다. 최소한 다음을 읽는다 (있는 것만):
   - `README.md`, `CLAUDE.md`, `DESIGN.md` 같은 설명 문서
   - `package.json` (또는 언어에 맞는 의존성 파일) — 어떤 라이브러리/프레임워크를 쓰는지
   - 실제 화면을 그리는 코드 (예: `app/`, `src/`, `components/`, `pages/` 등) — 화면에 뭐가 보이는지
   - 데이터를 다루는 코드/파일 (예: `data/`, `lib/`, DB 스키마 등)
2. 필요하면 Glob/Grep으로 더 찾아본다. 파일 하나만 보고 넘겨짚지 않는다.
3. 아래 세 질문에 순서대로, 각 질문마다 **결론 → 근거(확인한 파일 경로 + 구체적으로 뭘 봤는지)** 순으로 답한다.

## 답해야 할 세 가지 질문

**1. 이 서비스가 없으면 사용자는 지금 뭐로 해결하고 있나? 그것보다 나은가?**
- 이 프로젝트가 대신하려는 일을 사람들이 지금은 무엇으로 하고 있을지 생각한다 (예: 메모장, 엑셀, 다른 사이트, 그냥 안 함 등).
- 지금 만든 것이 그 대안보다 실제로 더 나은 점이 있는지, 아니면 그냥 다시 만든 것뿐인지 판단한다.
- 화면/기능 어디를 보고 그렇게 판단했는지 파일 근거를 남긴다.

**2. 화면에 있는 기능 중, 없어도 되는 건 뭔가?**
- 실제 화면 코드를 열어서 어떤 요소/버튼/섹션이 있는지 나열한다.
- 그중 핵심 목적과 상관없이 붙어 있는 것, 안 써도 사용자가 불편하지 않을 것 같은 걸 지목한다.
- "이 파일의 이 부분을 보니 이런 기능이 있는데, 이건 왜 있는지 불분명하다" 식으로 구체적으로 짚는다.

**3. 이 기술을 왜 썼나? 더 단순한 방법은 없었나?**
- `package.json` 등에서 쓰고 있는 프레임워크/라이브러리를 확인한다.
- 프로젝트 규모(파일 개수, 기능 복잡도)에 비해 과한 기술은 없는지 본다 (예: 정적인 페이지 하나에 무거운 프레임워크나 데이터베이스를 쓰는 경우 등).
- 있다면 더 간단한 대안(예: 그냥 HTML 한 장, 정적 파일)이 있었는지 짚는다. 과하지 않다면 "과하지 않다"고 명확히 말하고 이유를 댄다.

## 답변 형식

- 한국어로, **CLI(터미널)를 처음 써보는 사람**도 이해할 수 있는 말로 쓴다. 전문 용어(SSR, 하이드레이션, 번들러 등)를 쓸 경우 괄호로 짧게 풀어준다.
- 각 질문 = 소제목 하나. 그 아래 결론 한두 줄 + 근거 bullet.
- 근거 bullet에는 반드시 파일 경로(`app/page.tsx` 등)를 포함한다. 어림짐작이나 "아마도"로 채우지 않는다.
- 평가가 후하든 박하든 솔직하게 쓴다. 단점이 없으면 없다고, 있으면 구체적으로 무엇이 문제인지 쓴다.
